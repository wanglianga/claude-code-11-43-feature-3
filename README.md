# 校园供餐多源数据质量与过敏原暴露覆盖分析工具

一款纯浏览器端（React 18 + TypeScript + Vite）的数据分析工具，帮助数据分析师判断五类来源数据——
**供应商成分、菜谱、厨房实际用料、餐次日志、学生饮食限制**——能否可靠关联，并量化过敏原暴露分析中
**多少记录有证据支持、多少存在候选待确认、多少因来源缺失无法判定**。

本次迭代新增**证据语义与推导**模块：从餐次的成分判断追到实际用料依据，区分
**哪些成分有记录支持、哪些只有计划或间接线索、哪些仍未知、哪些材料相互矛盾**，
并支持补证/撤回/更正范围后的**定向重算与结论维护**。

- 不调用任何真实学校服务，不上传个人数据；所有数据保存在浏览器本地 IndexedDB。
- 读取随项目提供的 CSV / JSON 样例（`public/sample-data/`，全部为虚构数据）。
- 未匹配记录一律计入「未知」，**不会被当成「没有过敏原」**；厨房 `PLANNED`（计划使用）不参与实际暴露计算。
- 证据模块同样不作食物安全放行或医疗诊断；「资料不足」不等于不含过敏原。

## 一、核心设计

### 1. 三桶证据口径（每条领餐记录恰好落入一桶）

| 桶 | 含义 | 进入条件 |
| --- | --- | --- |
| 有证据支持的匹配 `CONFIRMED` | 链接链完整、原料解析有证据 | 供应商**精确编码**、**已批准别名**或分析师**人工确认**，且餐次/用料/限制链路完整 |
| 存在候选但需确认 `CANDIDATE_PENDING` | 有名称/规格/单位/成分候选，但未确认 | 候选**确认前不进入正式统计**，不低报暴露 |
| 来源缺失无法判定 `UNKNOWN_MISSING` | 来源缺失或链接断裂 | 区分空餐次、关联不存在、时间无法归属、批次未到齐、限制为空/未生效等具体原因 |

精确匹配与上下文候选**并行**：只有精确编码/批准别名自动生效；候选经分析师确认后才复用该决定。

### 2. 字段四态（不折叠成同一个失败数）

- `FIELD_NOT_PROVIDED` 源文件未提供该字段（如乙校供应商文件没有 `cert_no` 列）
- `VALUE_EMPTY` 字段值为空（甲校部分行 `cert_no` 留空）
- `REF_NOT_FOUND` 关联对象不存在（领餐→餐次、餐次→菜谱、限制学生→领餐）
- `BATCH_PENDING` 来源批次尚未到齐（`kit-b-2`，预期 6 行）

### 3. 不可变运行与版本固定

每次分析运行固定引用：**全部输入文件 SHA-256、映射版本+修订号、规则版本（rules-v1）**。
补发旧数据或修改映射后生成的是**新运行**，历史运行不被静默改写；「运行对比」页展示三桶迁移矩阵、
覆盖率变化与质量问题增减。

### 4. 映射乐观锁（多标签页）

保存映射时重新读取 IndexedDB 校验修订号；另一标签页已提交更高版本时，后提交者保存被拒绝并提示重载，
已确认映射不会被覆盖（同时通过 `BroadcastChannel` 主动推送版本变化）。

### 5. 证据语义与推导（本迭代新增）

**七类输入材料 + 转抄材料**分别表达：计划配方、领料事实、实际投料（含未投料记录）、制作分锅、
替换适用范围、发餐去向、商品成分声明（含有/可能含有/明确未检出，连同适用配方与批次）。
每项材料保留身份、来源批次、有效范围、原始行与更正关系；证据关联连接材料与制作批次、锅次、窗口及餐次。

**六态判断分别表达，不折叠成可信分数**（`src/evidence/derive.ts` 由材料实际生成，非静态等级表）：

| 状态 | 进入条件 |
| --- | --- |
| 实际批次已确认含有 | 实际投料 + 商品成分声明（含配方/批次）+ 发餐关系齐备的完整路径 |
| 标签提示可能含有 | 链路完整但声明为「可能含有」 |
| 计划中使用 | 计划配方使用该成分，但无覆盖全部范围的实际投料记录 |
| 有间接线索 | 领料进厨房（≠投进每锅）、缺批次声明的投料、转抄材料 |
| 资料不足 | 无完整且适用的支持路径；不等于不含，不能统计为无过敏原 |
| 材料冲突 | 同范围内已确认含有依据与明确相反记录并存，双方原件并列不投票 |

关键口径：

- **确认门槛**：领料进厨房不证明投进每锅；计划配方不能补成实际投料；空白配料栏、缺少声明、
  没有检索命中均不构成不含证据。
- **替换记录**含被替换原料、替代原料、适用锅次与是否全量；范围未登记时保留仍成立的用料解释，
  不因备注「已替代」删除整日关联（样例 `SUB-A-OIL`）。
- **合并发餐**：能确认餐次存在含有记录不代表所有份数都含有；无逐份去向时不推测个体摄入，
  已确认暴露份数只计可归属部分。
- **冲突**：仅同范围（同锅/同批次）的相反记录构成冲突；不同锅次、不同批次的相反记录按范围各自保留。
- **来源追踪**：引用闭包归并到根原件区分独立支持与转抄（厨房日报与窗口汇总引用同一领料单不升级为
  多方证实）；循环引用不产生事实支持，但另有独立原件的路径仍单独成立。
- **撤回维护**：沿反向依赖找到受影响判断并重算；有替代完整路径则说明保留原因，最后一条支持撤回后
  转为资料不足（待核），不沿用已确认标签，也不证明相反结论。

**实现方式选型（定向重算）**：本模块保存每项判断的支持路径与反向依赖索引（`DerivationStore.reverseIndex`），
材料变化时只重算受影响判断。另一方案是每次分析前按目标餐次重新展开全部材料——它纠错时几乎不维护
中间状态，更适合材料一次写入后很少补证、或分析频次很低的场景；但同批材料被许多窗口复用时会反复求值，
批量查看需要等待。当前方案在反复分析与补证反馈上更快，代价是要维护多条替代路径的存储与正确性
（撤回、部分适用、共用原件），路径存储也随之增加。两种方案都必须可追查且一致：页面提供
「全量重算校验」，测试中以 `verifyAgainstFullRecompute` 断言定向更新结果与从零全量推导完全一致
（无遗漏、无无依据的确认结果）。

**提交与恢复**：补证/撤回/更正先预览影响（受影响餐次、成分、已确认/未知数量），再提交；
材料库提交走 IndexedDB 事务内的原子比较并写入（乐观锁），计算期间被另一标签页更正的完成结果只留作
旧资料计算，不覆盖当前推导；已提交材料、未完成计算任务、未提交预览草稿分别持久化，
关闭页面后分别恢复，当前推导整体原子替换，不会出现一半餐次已更新、一半仍引用旧支持。
推导运行快照不可变，旧运行保留当时解释，不被新证据静默替换。

## 二、目录结构

```
public/sample-data/          随项目提供的样例输入（CSV/JSON + manifest + 种子映射）
  manifest.json              批次清单（含晚到批次 sup-a-2、未到齐批次 kit-b-2）
  standard_ingredients.json  10 种标准原料及其过敏原
  seed_mappings.json         初始映射（批准别名 + 人工确认决定）
  schoolA/ schoolB/ meal/ diet/
  evidence/                  证据模块样例：七类材料 + 转抄 + 补证批次 + 成分映射参考
src/
  lib/        CSV 解析、SHA-256、IndexedDB 封装、数据加载、导出、批次统计
  engine/     规则、上下文索引、质量检查、匹配引擎、运行引擎与对比/预览（纯函数，可单测）
  evidence/   证据模块：材料层、引用图（转抄/循环/独立支持）、六态推导、
              推导库（反向依赖 + 定向重算 + 全量校验 + 影响预览）（纯函数，可单测）
  state/      React 全局状态、IDB 持久化、乐观锁（映射 + 证据材料）
  components/ 共享组件（徽标、抽屉、覆盖图、六态徽标）
  pages/      总览 / 来源批次 / 映射工作台 / 质量检查 / 分析运行 / 运行详情 / 运行对比 / 证据与推导
Dockerfile + docker-compose.yml + nginx.conf   一键静态部署
```

## 三、本地启动

### 方式 A：Node 开发服务器（推荐用于本地开发）

要求 Node.js 22（容器内固定入口 `/opt/node-22/bin/node`）。

```bash
npm install --registry=https://registry.npmmirror.com
npm run dev        # http://localhost:5173
```

生产构建与本地预览：

```bash
npm run build      # 类型检查 tsc -b + vite build，产物在 dist/
npm run preview    # http://localhost:4173 静态预览（含 SPA 回退）
```

> 必须通过 HTTP 服务访问（需要 `fetch` 读取样例数据），不要直接双击打开 index.html。

### 方式 B：Docker / Compose 一键启动

```bash
docker compose up --build
# 打开 http://localhost:8080
```

多阶段构建：node:22-alpine 构建静态资源 → nginx:1.27-alpine 托管（已配置 SPA 路由回退）。
停止：`docker compose down`。

## 四、测试账号与隐私说明

本工具**没有登录体系、没有后端、没有测试账号密码**：

- 样例学生均为匿名学号（`S-1001` … `S-1023`、`S-9999`），由校医维护的饮食限制按匿名学号生效。
- 所有映射、人工确认、分析快照与运行结果仅写入浏览器 IndexedDB（库名 `campus-meal-dq`）。
- 「分析运行」页提供「重置工作区」，可清空本地数据并恢复随项目提供的种子映射。
- 可在浏览器 DevTools → Application → IndexedDB 中核查全部本地数据，不存在任何网络上报。

## 五、验证方式（建议操作路径）

1. **总览页**：查看 11 个来源批次的输入/有效/重复/关联/未知行数与三桶覆盖环形图；点开「指标详情」查看分子、分母、排除条件、来源范围。
2. **来源批次页**：打开 `sup-b-1` 看到 `cert_no` 为「源文件未提供」；打开 `sup-a-1` 看到 3 行「字段值为空」；打开 `kit-b-2` 看到「批次尚未到齐」；可逐行下钻原始行。
3. **质量检查页**：核对重复键、缺失键、单位冲突、时间无法归属、多对多连接五类问题并下钻原始行。
4. **映射工作台**：在「菜谱/厨房简称」中找到待确认候选「芝麻」（影响餐次 MS-A-0901-D / 领餐 SV-006），
   点「预览影响」→ 看到候选 1→0、确认 4→5、未知 19 不变 → 「保存并生成新运行」。
5. **分析运行 → 运行详情**：三桶筛选、逐层下钻（计算轨迹、参与计算的厨房实际用料原始行与映射决定、领餐原始行），
   导出 JSON（含运行编号、口径摘要、未知范围与免责声明）或 CSV。
6. **运行对比**：选择两个运行，查看桶位迁移矩阵与覆盖率变化；旧运行保持不变。
7. **多标签页冲突**：再开一个浏览器标签页，在两个标签页同时编辑映射，后保存者收到版本冲突横幅且保存被拒绝。
8. **证据与推导（新）**：
   - 「餐次判断」页签查看 10 项判断的六态分布；展开餐次 `MS-A-0901-L` 看到锅次 POT-A1（实际投葵花籽油 +
     芝麻未检出声明）与 POT-A2（无投料记录缺口），芝麻=计划中使用、花生=标签提示可能含有；
     点开「支持路径/缺口/冲突」查看完整链路、替换范围未登记的保留说明与合并发餐提示。
   - 「餐次判断」中 `MS-B-0901-L · 蛋` 为材料冲突：抽屉内并列投料+声明与未投料记录双方原件。
   - 「材料台账」撤回 `DEC-MILK-A1` → 预览显示 `MS-A-0901-B · 乳` 仍为已确认（独立支持 DEC-MILK-A2 保留原因）→
     提交；再撤回 `DEC-MILK-B1` → `MS-B-0901-B · 乳` 转为资料不足（不等于不含乳）。
   - 「材料台账」对 `SUB-A-OIL` 更正范围为指定锅次 POT-A1（全量）→ 预览确认整日芝麻油关联不被删除。
   - 「补证与预览」导入补证批次 `ev-supp-1`（2 号锅芝麻油投料补录）→ 预览：芝麻 计划中使用→已确认含有 →
     提交后查看发餐范围：合并发餐 5 份、可归属 0 份（不按整餐份数计暴露）。
   - 「推导运行」点「全量重算校验」确认定向重算与从零推导一致；查看旧运行快照保持当时解释；
     导出 JSON/CSV 与页面统计同源。
   - 刷新或关闭重开页面：已提交材料、当前推导、未提交预览分别恢复；再开标签页提交更正，
     本标签页收到材料版本冲突提示。
